# 예외

- 비정상 흐름을 표현하는 객체

```java
int result = 10 / 0;
```

- `ArithmeticException` 발생

## 계층 구조

```java
Object
  └─ Throwable
      ├─ Error
      │   ├─ OutOfMemoryError
      │   └─ StackOverflowError
      │
      └─ Exception
          ├─ IOException
          ├─ SQLException
          │
          └─ RuntimeException
              ├─ NullPointerException
              ├─ IllegalArgumentException
              ├─ IllegalStateException
              └─ ArithmeticException

Exception
├─ RuntimeException        → Unchecked
└─ 그 외 Exception         → Checked
```

- Error
  - JVM 레벨의 심각한 문제
  - 앱에서 처리하지 않음
- Checked Exception
  - 컴파일러가 처리를 강제
  - `catch`, `throws`
- Unchecked Exception
  - 처리를 강제하지 않음
  - 필요한 계층에서 처리

## Checked Exception

```java
public String readFile() throws IOException {
    return Files.readString(Path.of("test.txt"));
}
```

- throws를 하지 않으면 `Unhandled exception: java.io.IOException` 에러를 띄움(처리를 강제)

```java
public static String readFile() {
    try {
        return Files.readString(Path.of("path"));
    }
    catch (IOException e) {
        System.out.println("Error reading file");
    }

    return null;
}
```

- 밖으로 던지거나 잡거나

### 왜 처리를 강제하는지?

- 외부의 요인으로 발생(`IOException`, `SQLException`)
- 처리를 통해 회복 가능한 예외
  - 처리 -> 흐름을 중단한다거나 자원을 반환한다거나
  - 흐름을 중단하지 않으면? 결제 실패 -> 배송 진행
  - `close()`를 안한 상태, 자원 고갈

## UnChecked Exception

- 회복이 불가능한 경우가 대부분
- 파일이 없는데 다시 읽어봐야 없음
- 로직의 오류
- 안해도 되지만 프로그램이 터지거나 `500`에러 반환

## 어떻게 처리?

- 전역 처리

```java
@RestControllerAdvice // 전역 어드바이스 설정
public class GlobalExceptionHandler {

    // IOException이 터지면 이 핸들러가 처리
    @ExceptionHandler(IOException.class)
    public ResponseEntity<String> handleIOException(IOException e) {
        return ResponseEntity.status(500).body("파일 처리 중 에러가 발생했습니다.");
    }

    // NullPointerException이 터지면 이 핸들러가 처리
    @ExceptionHandler(NullPointerException.class)
    public ResponseEntity<String> handleNullPointer(NullPointerException e) {
        return ResponseEntity.status(500).body("서버 내부 데이터 오류가 발생했습니다.");
    }
}

// 언체크는 자동으로 받을 수 있음 -> NullPointerException
// 체크는 래핑해서 던지면 받을 수 있음
try {
    // 체크 익셉션을 던지는 외부 작업
    file.read();
} catch (IOException e) {
    // 언체크 익셉션으로 포장해서 던짐!
    throw new RuntimeException("파일 읽기 실패", e);
}

Throwable cause = e.getCause();

if (cause instanceof IOException) {
    // 아! 이건 원래 IOException 때문에 발생한 런타임이구나!
    System.out.println("파일 입출력 문제로 터진 런타임입니다.");
} else if (cause == null) {
    // 원인이 없다면 그냥 순수하게 코드에서 발생시킨 런타임(예: NullPointerException 등)이구나!
    System.out.println("순수 런타임 에러입니다.");
}
```

### 커스텀 예외를 만들어 던지자

```java
// 1. 내가 만든 커스텀 언체크 익셉션
public class FileReadException extends RuntimeException {
    public FileReadException(Throwable cause) {
        super(cause); // 부모(RuntimeException)에게 원인을 전달
    }
}

try {
    file.read();
} catch (IOException e) {
    // 2. IOException을 감싼 '전용 런타임 예외'로 포장해서 던짐
    throw new FileReadException(e);
}

@ExceptionHandler(FileReadException.class)
public ResponseEntity<String> handleFileReadException(FileReadException e) {
    // 이 핸들러는 오직 '파일 읽기 실패' 때문에 난 런타임만 전용으로 처리함!
    return ResponseEntity.status(500).body("파일을 읽는 도중 문제가 발생했습니다.");
}

@ExceptionHandler(NullPointerException.class)
public ResponseEntity<String> handleNullPointer(NullPointerException e) {
    // 이건 순수한 널 포인터 처리
    return ResponseEntity.status(500).body("서버 내부 코드 오류가 발생했습니다.");
}
```

## 체크 익셉션은 트랜잭션 롤백을 하지 않는다.

- 체크 -> 처리필수 -> 개발자가 뭔가 의도를 가지고 처리했을듯
- 언체크 -> 로직을 잘못씀 -> 즉각 복구
- 실제로는 `rollbackFor`로 복구하게 하는게 대부분
